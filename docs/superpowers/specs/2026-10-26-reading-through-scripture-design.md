# Reading Through Scripture: design and project plan

## Context

Matt wants a native Apple app for reading through the Bible in a year, first on macOS and then mirrored on iOS, with the two sharing one codebase and syncing through iCloud. Beyond plain reading, the app is a study notebook: partial-verse highlights in user-defined colors, markdown notes linked to those highlights, bookmarks, and an LLM assistant that can answer questions about a selection or produce chapter studies from editable prompt templates. Apple's on-device Foundation Models framework should carry the LLM work when it can, with Anthropic, OpenAI, or any OpenAI-compatible endpoint as cloud options behind a user-supplied API key. The repo at `/Users/matt/Code/reading-through-scripture` is empty apart from `.git`.

The outcome this plan drives toward: a macOS app Matt can use for his daily reading within the first milestones, with the architecture already shaped for iOS and sync so those arrive without rework.

## Goals, non-goals, anti-goals

**Goals**
- Fast, quiet reader for eight bundled English translations, ESV default, that reopens where you left off.
- Markup that feels like a paper Bible plus a notebook: phrase-level highlights, linked notes, bookmarks, copy and share.
- LLM help that knows where you are: ask about a selection, run chapter prompts, keep conversations per book and chapter, save replies as notes.
- Works with zero setup via the on-device model; cloud models when a key is entered.
- Everything the user creates syncs through their private iCloud and shows up on iPhone and iPad.

**Non-goals for v1 (leave room, build nothing)**
- Reading plans and "today's reading." The church plan arrives as a PDF and will not be hard-coded.
- Audio reading. Verse-addressable text already makes a future read-aloud mode possible.
- App Store distribution. Personal use only until ESV licensing is sorted.
- Multi-user or shared notes.

**Anti-goals**
- A reader that feels like a web page or a database browser. Typography and whitespace matter more than chrome.
- LLM output that silently replaces reading. The assistant lives in a side panel and never rewrites or annotates the text on its own.
- Sync that loses or duplicates highlights. Last-writer-wins per record is acceptable; data loss is not.

## Constraints

- Native Swift and SwiftUI only. Minimum macOS 26 and iOS 26, because Foundation Models requires them. Matt's Mac is on macOS 26.3.1.
- No paid Apple Developer account yet. Everything except CloudKit sync and real-device iOS testing can be built and run with a free personal team. CloudKit needs the paid program, so sync is scheduled after the account exists.
- Bible text comes from `https://github.com/bobuk/holybooks` (BSD-3 for the layout; the copyrighted translations ESV, NASB, AMP, ERV are Matt's call and acceptable for personal use). All eight translations are bundled; BOOKS (26 NT books only) is skipped.
- Anthropic has no official Swift SDK, so cloud calls use URLSession against `POST /v1/messages` with `anthropic-version: 2026-10-21`, streaming via Server-Sent Events, default model `claude-opus-5-5`. OpenAI and compatible endpoints use `/v1/chat/completions` with SSE.
- The on-device model has a context window of about 4,096 tokens shared by prompt and reply. Most chapters are 400 to 1,600 words, but Psalm 119 is about 2,400 words, so routing must check size.

## Decisions made in the conversation

### Navigation
- First launch shows the front page: Old Testament and New Testament book lists. Selecting a book shows a chapter grid (quiet numbers, five across, book name as header, matching Matt's screenshot). Book list and grid sit on one screen so you can hop between books.
- The app always reopens to the last reading position, including scroll offset. Home button in the toolbar returns to the front page without losing that position.
- ⌘K command palette: fuzzy search for books, references like "Rom 8" or "John 3:16" (verse references scroll to the verse), notes, settings, translation switch, and commands such as "Toggle notes column."

### Reading
- ESV default; translation switchable from the toolbar pill, settings, and ⌘K.
- Verse numbers as small superscripts; poetry lines preserved from the source data; chapter heading is clickable and opens the LLM prompt menu.
- Chapter-level notes display in a band under the heading, never as a highlight over the chapter body.

### Markup
- Highlights attach to a character range within a verse; partial verses are normal. Overlapping highlights are allowed.
- Five default colors; the user can add more, each with a name. Managed in settings.
- Notes are markdown, tied to a highlight or verse range, and record created and modified timestamps, reference, translation, and the quoted text at the time of writing.
- Notes column on the right shows this chapter's notes. Highlights without notes also appear as compact single-line rows; a setting hides them. A single click on a compact row focuses the highlight in the text and expands the row into a card with an empty note field; the note is created when the reader clicks into that field, and a field left empty collapses back to the row.
- Selecting a highlight lights its card and vice versa; clicking anywhere on a card (outside its editor) scrolls to and outlines the highlight and lights that card. A selected card uses the standard list-selection look: a subtle accent-tinted rounded background, text colors unchanged.
- Every card follows one rule: a single click selects it and focuses its highlight; a second click into the note text (or the empty field of an expanded row) enters edit mode. The color dot on a card or row opens a popover with the swatches plus "No color" (underline only), and choosing one recolors that highlight at once.
- Notes are edited in a plain markdown editor with a small toolbar above it: Bold, Italic, Heading, Bulleted list, Link (SF Symbols `bold`, `italic`, `textformat.size`, `list.bullet`, `link`). Each button toggles its markdown syntax on the selection (or the selected lines), so pressing it twice restores the text. Rendered markdown (emphasis, headings, lists, links) shows when not editing.
- Finishing an edit: Return inserts a newline and ⌘Return commits by default; the setting "Finish editing with" offers ⌘Return (default) or Return (then Shift-Return inserts a newline). Clicking outside the editor also commits. A Done button exists but is never required. Deleting a note works while it is being edited.
- A note added to a selection without choosing a color anchors to the exact phrase and shows as a thin dotted underline. A color can be added later from the context menu. Data-model consequence: every note on text is attached to an anchor record (the `Highlight` model) whose `colorID` is optional; no color renders as the underline.
- Bookmarks are whole-verse, even if the selection was partial. Margin glyph using SF Symbols. All icons use SF Symbols, never emoji.
- Selecting text: drag-selecting in the reader opens the markup menu on mouse-up, anchored below the start of the selection the way a selection toolbar sits with the text; right-click opens it at the pointer. Selections snap to whole words (verse numbers and the separators between verses stay excluded). A single click on a word inside an existing highlight acts on that whole highlight: the highlight keeps its own color and is outlined (no text-selection color over it), and the menu opens for it; nested highlights resolve to the innermost one. Highlights made in another translation (shown on the whole verse) count the same way.
- Selection actions via context menu: color swatches plus "No color" (inside a highlight) and "+" first, then Add Note or Edit Note, Remove Highlight (whenever the click or selection lies inside a highlight; removes the highlight with its note), Bookmark, Copy, Copy with Reference, Share (system share sheet), Ask about this passage.
- Separate Notes view: all notes, highlights, bookmarks and chat threads across the Bible, sortable by date or reference, with full-text search.

### LLM
- Ask: the notes column swaps to a chat panel scoped to the selection. The prompt carries reference, selected text, and translation. Each reply has Copy and Add as Note. Adding saves a note attached to the selection with question and answer in the body.
- Conversations are kept and reopenable. Each thread has a scope: selection, chapter, or book. The chat panel's history list is filtered to the current location; a book-level thread persists across chapters, and new questions from a new chapter append the new reference and text so the model knows where the reader has moved. Threads appear in the Notes view.
- Chapter prompt templates, enabled by default: Overall summary, Key themes, Cross-references, Catch me up, Outline, Context, People and places, Hard verses, Reflection questions, Word study, Memory verse. Templates are editable, deletable, re-orderable, and new ones can be added. Placeholders: `{{reference}}`, `{{chapter_text}}`, `{{translation}}`, `{{selection}}`, `{{previous_chapter_text}}` (used by Catch me up).
- Selection-level built-in prompts: Explain this, Define words, Compare translations (the app supplies the other bundled translations' text itself).
- Routing: Apple Foundation Models is the default when available and the request fits its window. A cloud provider is used when a key is configured and the user picks it, or automatically when the request is too large for the on-device model. The panel labels which model answered.
- Providers: Apple on-device, Anthropic, OpenAI, OpenAI-compatible (custom base URL and model name). API keys live in the Keychain with iCloud Keychain sync so they are entered once.

### Sync and iOS
- SwiftData with CloudKit private database. Bible text never syncs; user data references `translation / book / chapter / verse / character offsets`.
- Synced: highlights, notes, bookmarks, chat threads and messages, prompt templates, highlight colors, reading position, settings.
- Conflicts: last-writer-wins per record.
- iOS is a full mirror. iPad keeps the side column; iPhone uses a bottom sheet for notes and chat; ⌘K becomes a search button plus the hardware shortcut when a keyboard is attached.
- Milestone 7 amendments (Matt, 2026-11-09; the plan at `docs/superpowers/plans/2026-11-09-milestone-7-sync.md` has the reasons):
  - Reading position and settings travel through the iCloud key-value store, mirrored onto the existing `UserDefaults` keys, not as `ReadingState` and `UserSettings` records. Text size, line spacing and appearance stay with each device.
  - The synced store is a new file. The old local store is copied into it once, by uuid, and is never changed.
  - Signing out of iCloud empties the synced store until the same account signs back in (Apple's design). The app therefore keeps a daily local backup, the last seven, and Restore brings back whatever is missing.
  - A Debug build has its own bundle ID, iCloud container, store and preferences, so development never touches the notes Matt reads with.
  - Sync shows as one line in Settings › General.

## My calls (not discussed; Matt can override)

- Reading position is stored per translation-independent location (book, chapter, first visible verse) so switching translation keeps the place.
- Highlight offsets are stored against the translation they were made in. When viewing another translation the app shows the highlight on the whole verse with a subtle dashed underline, since the character range cannot be mapped.
- Chat message history for the on-device model is trimmed to fit the window; cloud providers get the full thread.
- The Foundation Models route uses a short instructions block plus the chapter text; `@Generable` structured output is used for Outline (sections with verse ranges) so it renders as a list, and plain text for everything else.
- "Copy with Reference" format: `“text” — Matthew 5:3 (ESV)`.
- Markdown rendering in notes uses `AttributedString(markdown:)` for display and a plain `TextEditor` for editing. No rich editor in v1.
- Highlight colors are stored as named entries with light and dark variants.
- **Too large for on-device, no cloud key:** the chat panel shows a short message that the passage is too long for the on-device model and offers a button to Settings to add a key. No chunking pipeline in v1. Two prompts are kept within the window on-device: Compare translations sends at most three translations at a time, and Catch me up sends the previous chapter's first and last five verses rather than the whole chapter when the full text would not fit. Book-level threads on-device keep only the last few exchanges plus the current reference.
- **Repository hygiene:** the generated `bible.sqlite` is not committed; the importer runs as a build phase (or a `make bible` step) that fetches the pinned holybooks commit into a cached directory outside the repo and writes the database into the build products. Test fixtures are copied only from public-domain translations (WEB and KJV), so no copyrighted text enters git history and the repo can be made public later. The CPDV or WEB Apocrypha serves as the third-canon fixture.

## Architecture

One Xcode workspace, one Swift package for everything shareable, two thin app targets.

```
ReadingThroughScripture.xcworkspace
├── Packages/ScriptureKit/            # Swift package, all platform-neutral logic
│   ├── Sources/ScriptureData/        # Bible text access (read-only SQLite), reference parsing
│   ├── Sources/ScriptureModel/       # SwiftData models, repositories, sync-safe ids
│   ├── Sources/ScriptureLLM/         # Provider protocol, Apple FM, Anthropic, OpenAI, routing, templates
│   ├── Sources/ScriptureUI/          # Shared SwiftUI views: Reader, NotesColumn, ChatPanel, Palette
│   └── Tests/                        # Unit tests for each module
├── Apps/Mac/                         # macOS app target: window, toolbar, menus, settings scene
├── Apps/iOS/                         # iOS app target: navigation stack, sheets
├── Tools/BibleImporter/              # Swift command-line tool: holybooks JSON → bible.sqlite
└── Resources/bible.sqlite            # Generated, bundled in both apps (~60-80 MB for 8 translations)
```

### Bible data pipeline (`Tools/BibleImporter`)
- Fetch the `EN/` tree of holybooks (pinned commit hash recorded in the repo) into a cache directory.
- Parse each `EN/{OT,NT,AP}/{BOOK}/{VERSION}.json`. Structure: `text` is a list of chapters, each with `ID` like `NT:MAT.5` and `text` as a list of entries `{ID, text}` where `ID` is the verse number. A verse may span several entries (poetry lines); empty entries mark line breaks. The importer merges entries by verse number into one verse record, storing line breaks as `\n` so the reader can render poetry.
- Output SQLite tables: `translation(id, title)`, `book(id, canon, order, name, short_name, chapter_count)`, `verse(translation_id, book_id, chapter, verse, text)` with an index on `(translation_id, book_id, chapter)` and an FTS5 table over verse text for ⌘K search.
- Book order uses the standard Protestant canon order for OT and NT; Apocrypha books (WEB, CPDV) go in a third section shown only when the active translation has them.
- `ScriptureData` reads this via GRDB or raw `sqlite3`; the recommendation is GRDB for its Codable row mapping and FTS support. This is the only third-party dependency.

### Data model (`ScriptureModel`, SwiftData + CloudKit)
CloudKit rules: every attribute has a default or is optional, no `@Attribute(.unique)`, all relationships optional. Each model carries a `uuid` for stable cross-device identity.

- `VerseLocation` (struct, Codable, stored inline): `book`, `chapter`, `verse`.
- `Highlight` (also the anchor for text notes): uuid, location, `startOffset`, `endOffset` (UTF-16 offsets within the verse in `translationID`), `translationID`, `colorID?` (nil renders as a dotted underline), `quotedText`, `createdAt`, `modifiedAt`, `note?` (one-to-one). A highlight with no color and no note is deleted.
- `Note`: uuid, `body` (markdown), `createdAt`, `modifiedAt`, `scope` (highlight / verseRange / chapter), `location`, `endLocation?`, `translationID`, `quotedText`, `highlight?`, `sourceThread?`.
- `Bookmark`: uuid, location, `createdAt`, `label?`.
- `HighlightColor`: uuid, `name`, `lightHex`, `darkHex`, `sortOrder`, `isDefault`.
- `PromptTemplate`: uuid, `title`, `body`, `scope` (chapter / selection), `isEnabled`, `sortOrder`, `isBuiltIn`, `outputKind` (text / outline).
- `ChatThread`: uuid, `scope` (selection / chapter / book), `location`, `endLocation?`, `translationID`, `title`, `createdAt`, `updatedAt`, `messages` (one-to-many).
- `ChatMessage`: uuid, `role`, `content`, `createdAt`, `providerID`, `modelName`, `attachedReference?`.
- `ReadingState`: single record. `currentLocation`, `firstVisibleVerse`, `translationID`, `updatedAt`.
- `UserSettings`: single record. `showNotelessHighlights`, `defaultProviderID`, `fontSize`, `lineSpacing`, `theme`.

### LLM layer (`ScriptureLLM`)
- `protocol LLMProvider { var id; var displayName; func stream(_ request: LLMRequest) -> AsyncThrowingStream<LLMEvent, Error>; var maxContextTokens: Int?; var isAvailable: Bool }`.
- `LLMRequest`: system instructions, message history, max tokens. `LLMEvent`: `.textDelta(String)`, `.done(usage)`, `.error`.
- `AppleFoundationProvider`: wraps `SystemLanguageModel.default` and `LanguageModelSession`, checks `availability` (device support, Apple Intelligence enabled, model downloaded), estimates tokens at roughly 1 token per 4 characters and refuses requests over about 3,000 tokens so routing can fall back.
- `AnthropicProvider`: URLSession to `https://api.anthropic.com/v1/messages`, headers `x-api-key`, `anthropic-version: 2026-10-21`, body `{model, max_tokens, stream: true, system, messages}`, parses SSE `content_block_delta` text deltas, checks `stop_reason` including `refusal`. Model defaults to `claude-opus-5-5`; user can change the model string in settings.
- `OpenAICompatibleProvider`: base URL + model string + key; used for both OpenAI and custom endpoints.
- `LLMRouter`: picks provider by user preference, availability, and fit. Emits the chosen provider so the UI can label the reply.
- `PromptBuilder`: fills template placeholders from `ScriptureData`, builds the system prompt (role: careful study assistant; cite verses by reference; say when uncertain; do not invent references).
- `KeychainStore`: wraps Security framework with `kSecAttrSynchronizable` for iCloud Keychain.

### UI (`ScriptureUI` plus app targets)
- `FrontPageView`: canon sections, book list, chapter grid.
- `ReaderView`: attributed verse rendering. On macOS use `NSTextView` via `NSViewRepresentable` for selection ranges, custom context menu, and highlight drawing; on iOS use `UITextView` via `UIViewRepresentable`. SwiftUI `Text` cannot report selection ranges, so TextKit 2 is the right tool here. Highlights draw as background attributes; bookmark glyphs in a gutter view.
- `NotesColumnView` / `ChatPanelView` share the right-hand slot with a navigation transition between them.
- `CommandPaletteView`: overlay window on macOS, sheet on iOS; backed by a `ReferenceParser` and FTS search.
- `NotesBrowserView`: the whole-Bible notes, highlights, bookmarks and threads list with search and sort.
- `SettingsView`: translations, highlight colors, prompt templates editor, providers and keys, notes column options, typography.
- macOS specifics: toolbar with Home, back/forward, reference crumb, translation pill, search field, notes toggle; menu bar with Go, Highlight, Notes, View menus mirroring the shortcuts.
