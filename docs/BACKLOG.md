## An older build meets a newer store (wanted; was to be milestone 12)

Matt, 2026-11-20: milestone 11 is UI improvements first; this comes in milestone 12. Matt, 2026-11-26: milestone 12 is the site instead (`docs/superpowers/specs/2026-11-26-milestone-12-site-design.md`); this still waits, wanted, for a later milestone.

- **Read-only when the store was opened by a newer version (wanted).** Matt's words: "If a store is detected from a newer version, the user is forced to update before editing or adding anything. However, I would like for them to still be able to read and open things, just not edit." He does not want every device to need updating at once (and it need not: across devices an older build is safe, rehearsed in projects 5 and 6). The hazard is an older build opening the *same* store file on the *same* device, which a reinstall of an older version or an old Debug build can do: Core Data migrates the store down and strips what that build does not know (plans and ticks; kept versions, deletion markers and a note's three version values), and only what had already reached iCloud comes back. The plan to rehearse first, since a claim about Apple's frameworks is a guess until rehearsed: an older build reads the store's own metadata before opening it (`NSPersistentStoreCoordinator.metadataForPersistentStore` against its model's compatibility check), so no new stored value is needed; on finding a newer store it opens a *copy* in a temporary folder, with sync off, and shows everything with editing off and one quiet line saying to update. The bulk of the work is turning off every way to edit (highlights, notes, bookmarks, plans and ticks, colours, prompts, conversations, import). Refusing outright (a "please update" screen) would be the smallest build; Matt chose read-only. Only builds that carry the check are protected, so it guards updates after the one that ships it, not the milestone 9 to 10 update. Needs a spec, mockups for the read-only state on both apps, and a rehearsal in the `.rehearsal` identity. Replaces the "refuse a store a newer build has used" items that projects 5 and 6 set aside.

## Keeping data safe (project 6)

Set aside by the spec, the plan, the whole-project review and the fix wave's re-review (the review's triage table sent each deferred line here or dropped it). The spec's section 11 has the known limits in full.


**Rules and data**

- **Removing same-identity copies safely.** Departure 1 reads copies as one and deletes none except a note's differing copy once kept. Two devices each deleting a different copy lose both (a delete always wins), so a safe removal needs a rule that tells the devices which copy to delete: until then the extras stay, and a twin prompt or colour moved down can read as reverted (`Twins.swift`, `PromptTemplateStore`, `MarkupStore`), of two twin highlights carrying a note the later `modifiedAt` wins and may carry the unread copy, and the "edited copy folds into a pristine survivor" step in `SeedMerge` still picks between twins by fetch order.
- **One device typing back its own earlier text exactly while another edits can lose that text.** Sight is by device and digest; closing this needs the sitting's token in each entry of an ancestry and a marker.
- **Discard the versions an import kept.** A note edited twice on one device since an export gets the file's old text as a kept version on import (Departure 6; the ancestry holds one entry per change of device, so the text from before two sittings is no longer named). Do not lengthen the ancestry: it widens the lost-text hole. An import that says "2 notes have another version kept" could offer to discard them as one step.
- **A removal that arrives before its marker, where the deleted text was a later edit, leaves one needless kept version with no note** (the re-review's m-1; the tidy-up removes an orphan only for the marker's first entry). Check in a two-stores-open rehearsal whether a marker and its note's removal ever arrive in separate imports.
- **The journal outlives its store (for Matt).** A store reset by hand or emptied by an account change turns every entry into a kept version with no note. A journal could remember the store's identity and drop entries whose store is not the one it was written for.
- **An unwritable journal folder gives a new device tag each launch, silently** (`LastTextJournal.swift`): protection is off in that state; add one log line at start.
- **A failed save can leave the journal and the store out of step once** (the journal forgets before a delete's save; `markNew` journals before the insert's save; a failed save after `settleEntry` has kept a draft loses the kept draft, the re-review's m-3). The next import settles all of it; a rollback-aware order would close it.
- **`deleteHighlight`** still says its marker is left "when it has text" and does not keep a note's other copies before deleting (they survive as notes, so nothing is lost).
- **An anchor left empty by a deleted copy** outlives the survivor's note and counts in the chapter rings (`VersionKeeper.swift`, M-13); apply the empty-highlight rule there.
